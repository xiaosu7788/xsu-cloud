# ARCHITECTURE — xsu-cloud

本文件回答「怎么分层、边界在哪、跑在哪里、能撑多少」。**A 级文档：模块边界变化时不同步就阻断合并。**

范围与验收标准见 [`PRD.md`](PRD.md)，强制约束与红线见 [`../AGENTS.md`](../AGENTS.md)。

---

## 1. 架构决策摘要

- **一个仓库、一个应用、一个部署单元。** 单体 Next.js 16 App Router，用路由组 `(site)` / `(console)` / `(admin)` 分区，不预先拆微服务。
- **五层分层 + 一条铁律。** 表现层 → 应用层 → 领域层 → 数据层 / 集成层。领域层不得依赖框架，集成层不得依赖领域层。
- **按模块拆分，不按技术拆分。** 将来要拆服务时，拆的是「社区」或「生图」这样的整块业务，而不是「前端服务 + 用户服务 + 内容服务」。
- **外部系统全部隔离在集成层。** 本项目不拥有任何外部系统的数据，只通过适配器读写。
- **公开内容默认静态化**，高频交互走独立轻量接口，重活交 worker。

## 2. 分层与边界

### 2.1 五层职责

| 层 | 位置 | 职责 | 明确不做 |
| --- | --- | --- | --- |
| 表现层 | `apps/web/app/(site\|console\|admin)`、`components/`、`features/`、`public/`（PWA 静态资源） | 渲染、交互、局部状态 | 不写业务规则，不直接访问数据库 |
| 应用层 | `apps/web/app/api/`、Server Actions | 解析入参、校验、鉴权、调领域层、组装响应 | **≤30 行**，不写业务规则，不拼 SQL |
| 领域层 | `packages/core` | 业务规则、状态机、权限判定、配额判定 | 不依赖任何框架，不依赖集成层 |
| 数据层 | `packages/db` | schema、迁移、仓储实现 | 不含业务规则 |
| 集成层 | `packages/integrations/*` | 调用外部系统并把结果翻译成本项目自己的类型 | 不知道业务规则，不依赖领域层 |

`packages/platform` 提供 auth / cache / queue 等基础设施，`packages/shared` 放无业务语义的工具与类型。两者可被领域层与应用层使用，但不得含业务规则。

### 2.2 依赖方向（强制）

```text
表现层
   │  可以依赖 ↓ 全部
   ▼
应用层
   │  可以依赖 ↓
   ▼
领域层 ─────────────┐
   │  可以依赖 ↓    │  禁止
   ▼                │
数据层          集成层
```

禁止项（ESLint `no-restricted-imports` 强制，按目录覆盖）：

| 来源 | 禁止 import |
| --- | --- |
| `packages/core` | `next`、`next/*`、`react`、`react-dom`、`server-only`、`packages/integrations/*` |
| `packages/integrations/*` | `packages/core` |
| 领域层与集成层 | `apps/web/*` |

### 2.3 这条规则换来什么

1. **热模块可整块搬走。** 社区压力变大时，把 `packages/core/community` + 对应仓储整块搬到独立 Hono 服务，同语言同类型，业务代码几乎不动。
2. **新外部系统只加目录。** 接入任何外部系统 = 在 `packages/integrations/` 下加一个适配器，领域层一行不改。

破坏依赖方向等于主动放弃这两个能力。这是本架构唯一不可妥协处。

## 3. 部署拓扑

### 3.1 单机服务清单

```text
                        Cloudflare（DNS / CDN / 证书 / 对象存储）
                                      │
                                      ▼
                    ┌─────────────────────────────────┐
                    │        单机 Docker Compose       │
                    │                                 │
                    │  web      Next.js 应用（无状态）  │
                    │  worker   BullMQ 消费者（无状态）  │
                    │  postgres 主库                   │
                    │  redis    会话 / 限流 / 队列      │
                    └─────────────────────────────────┘
```

| 容器 | 作用 | 状态 |
| --- | --- | --- |
| `web` | Next.js 应用 | 无状态，可横向加 |
| `worker` | BullMQ 消费者：生图轮询、发邮件、清理任务 | 无状态，可横向加 |
| `postgres` | 主库 | 有状态，备份重点 |
| `redis` | 会话、限流、队列（队列需开 AOF） | 有状态，可接受丢失但队列丢失会丢任务 |
| `minio` | **仅本地开发**的对象存储替身 | 生产由 Cloudflare R2 承担 |
| `mailpit` | **仅本地开发**的收信工具 | 生产由真实 SMTP 承担 |

生产环境不跑 `minio` 与 `mailpit`。反向代理与 HTTPS 由 Cloudflare 承担，应用不必直接暴露公网端口（可用 Cloudflare Tunnel）。

### 3.2 外部依赖

| 依赖 | 用途 | 失败时的影响 |
| --- | --- | --- |
| Cloudflare R2 | 图片与文件存储、CDN 源站 | 图片不可读；上传失败；**不影响已有页面渲染** |
| SMTP 服务 | 邮箱验证、找回密码、邀请邮件 | 注册与找回流程不可用；已有会话不受影响 |
| 外部数据源（可多个） | 中转站只读展示、生图任务 | 对应模块降级提示，**不得影响其他模块** |
| OAuth 提供方 | 第三方登录 | 该登录方式不可用，邮箱密码仍可用（若已实现） |

**原则：任一外部依赖不可用时，其影响必须被限制在对应模块内。** 这是适配器隔离的直接目的，也是 [`PRD.md`](PRD.md) 中转站验收标准第 1 条的来源。

### 3.3 境外部署的特殊性

- **免备案**，但**要注意跨境延迟**：境外到大陆的 RTT 通常 150–300ms 且晚高峰抖动明显。CDN 只能救静态资源；登录、发帖、提交任务等动态请求每个都要跨境。
- **因此**：公开页必须静态化（红线 1 不只是性能优化，是体验底线）；接口要减少往返次数（合并请求、乐观更新）；机房应选香港 / 日本 / 新加坡，不选美西。
- **数据出境**：用户个人信息存于境外，需在隐私政策中告知（见 [`PRD.md`](PRD.md) 4.4）。
- **对象存储放 R2 而非自建 MinIO**：R2 出口流量费为 0，而生图工作台要长期承担图片读取流量；且自建需要自己写备份与灾备，在单机上是最高风险项。

### 3.4 从单机到多机的迁移路径

只要坚持以下三条，加机器不需要改代码：

1. 应用与 worker 无状态，会话在 Redis / 数据库；
2. 文件全部在对象存储，不在本地磁盘；
3. 上传走预签名直连对象存储，不经应用进程。

## 4. 并发与容量策略

按「先便宜、后昂贵」的顺序逐档使用，不到必要不进入下一档：

| 档 | 手段 | 适用 | 代价 |
| --- | --- | --- | --- |
| 1 | 静态化 / ISR + CDN | 公开内容页、首页、工具说明 | 无（首选） |
| 2 | 独立轻量接口 + Redis 缓存 + 游标分页 + 索引 | 轮询、点赞、阅读数、列表 | 需要设计缓存失效 |
| 3 | 异步任务 + BullMQ worker | 生图、批量、邮件、清理 | 需要状态机与超时收敛 |
| 4 | 应用多副本 | 单机 CPU 打满 | 应用必须无状态（见 3.4） |
| 5 | 把热模块整块拆成独立服务 | 单一模块独占资源 | 需要运维第二套进程 |

**第 5 档拆的是模块，不是技术层。** 拆「社区服务」，不拆「用户服务 + 内容服务 + 通知服务」。

## 5. 数据模型分区

详细表结构见 [`DATA-MODEL.md`](DATA-MODEL.md)（M1 建立：鉴权四表 + 邀请码表）。此处只固定分域与关键设计点。

| 域 | 核心表 | 关键设计点 |
| --- | --- | --- |
| `accounts` | `user`、`session`、`account`、`verification`、`invites`（M4 再加 `external_identities`） | **不在 `user` 上硬写某一个外部系统的 ID**：登录用的第三方身份挂在 `account`，以 `(provider_id, account_id)` 标识（表名与字段见 [`DATA-MODEL.md`](DATA-MODEL.md)）；外部系统的用户级映射留到 M4 的 `external_identities`。任何外部系统都能挂，换源不返工 |
| `community` | `posts`、`comments`、`reactions`、`tags`、`reports` | `reactions` 靠唯一约束防重复点赞；列表走游标分页 + 复合索引 |
| `tools` | `tools`、`tool_runs`、`tool_favorites` | `tool_runs` 存输入输出摘要与耗时用于配额与审计，**不存敏感内容** |
| `genimage` | `image_jobs`、`image_assets`、`image_presets` | `image_jobs` 存外部任务 ID 与状态机；`image_assets` 只存对象存储 key 与元数据，**不存二进制** |
| `ops` | `audit_logs`、`api_usage`、`settings` | `audit_logs` 只追加不更新；`settings` 集中放可调开关 |

### 5.1 资源归属（强制）

每张业务表必须包含能回答「这是谁的」的字段（通常是 `owner_id`），并且：

- 跨用户访问的拒绝逻辑写在**领域层**，不在路由或页面里；
- 必须有测试覆盖跨用户访问被拒；
- 软删除字段与归属字段需同时出现在列表查询的索引中。

## 6. 关键流程

### 6.1 一次普通请求

```text
浏览器 → CDN / 静态缓存（命中即返回，不进 Node）
      → 未命中：表现层 RSC / 客户端组件
      → 应用层：Zod 校验 → 鉴权 → 配额判定（Redis）
      → 领域层：业务规则
      → 数据层 / 集成层
      → 响应
```

应用层只做编排，**任何业务判断都不在这里**。

### 6.2 生图任务全链路（关键流程）

```text
1. 用户提交参数
     → 应用层校验 + 配额
     → 领域层建 image_jobs（状态：排队）
     → 入队 BullMQ → 立即返回任务 ID（不阻塞请求）

2. worker 消费
     → 调外部数据源提交任务，存外部任务 ID（状态：进行中）
     → 按合适间隔轮询外部状态（使用同一个凭证）

3. 外部返回成功
     → 立即把结果抓取并转存到本项目对象存储
     → 写 image_assets（自己的 key），状态置为「成功」

4. 失败 / 超时
     → 状态置为「失败」或「超时」，绝不停留在「进行中」

5. 用户查看进度
     → 只轮询本项目自己的轻量接口（Redis 缓存），不直连外部源
```

**第 3 步不可省略。** 外部返回的是临时签名链接（约 24 小时过期），不转存就等于用户的历史任务会变成死链，且无法恢复。

## 7. 横切设计

### 7.1 对象存储

- 接口只认 S3 兼容 API，**不用任何厂商专用 SDK**（换供应商只改 endpoint 与凭证）。
- 分桶：`public`（可 CDN 公开读）与 `private`（签名 URL）。
- 上传走向：`客户端 → 预签名直传 → 对象存储`，**文件不经 Node**（红线 3）。
- 应用进程内不做图片处理；需要压缩或转码一律交 worker（红线 4）。

### 7.2 缓存

| 缓存对象 | 位置 | 失效策略 |
| --- | --- | --- |
| 公开页面 | CDN / ISR | 按标签或时间重新验证 |
| 列表与计数 | Redis | 短 TTL + 写时失效；计数可容忍短暂不一致 |
| 会话与限流计数 | Redis | 随会话 / 时间窗过期 |

### 7.3 队列

- 消费者：`worker` 进程，与应用同代码不同入口。
- 任务类型：生图提交、生图轮询、结果转存、邮件发送、过期清理。
- **必须有幂等键与超时收敛**，否则重试会重复提交外部任务，或留下永久「进行中」。
- Redis 队列需开 AOF，否则重启会丢任务。

### 7.4 响应式原语（移动端）

移动端适配不是样式问题，是设计系统层的能力。**M1 已在 `apps/web/components` 建立**（本节在 M1 之前只有一份清单）：

| 原语 | 解决的重复问题 | 落点与入口 |
| --- | --- | --- |
| `ResponsiveNav` | 桌面侧边栏 / 移动底部 Tab 两套壳 | `responsive-nav.tsx`；`NavItem = { href, label, icon?, exact? }`，移动 Tab 上限 `MOBILE_TAB_MAX = 5` |
| `ResponsiveTable` | 后台与控制台的宽表在移动端降级为卡片列表 | `responsive-table.tsx`；一份 `columns` 同时驱动表头与移动端「字段名 + 值」，`primary` 列作卡片标题 |
| `ResponsiveGallery` | 生图结果的滑动与全屏查看 | `responsive-gallery.tsx`；移动端滚动吸附横滑，桌面端补翻页按钮 |
| 断点常量 | 避免各模块自行写断点值 | `breakpoints.ts`；`BREAKPOINTS` / `BREAKPOINT_PX` / `atLeast` / `below` |

形态切换默认交给 CSS（`hidden lg:flex` / `lg:hidden`），不用 JavaScript 判断视口——服务端与首屏渲染的结构才一致。唯一例外是「按钮的有无改变 DOM」的场景（`ResponsiveGallery` 的桌面翻页按钮），那里必须用 JavaScript 判断。

这些原语必须先于业务模块建立。否则每个模块都会各自 hack 一套，后期统一等于重写布局。

## 怎么验证

- **分层边界**：`pnpm lint` 必须能拦住 `packages/core` 中的框架 import，以及 `packages/integrations` 中对 `packages/core` 的 import。已实跑验证（2026-09-30，见 [`ROADMAP.md`](ROADMAP.md) M0「状态」）；行为由 `packages/config/eslint/tests/layering.test.ts` 锁定。
- **应用层厚度**：检查 `app/api` 下每个 Route Handler 的行数，超过 30 行需说明理由或重构。
- **外部依赖隔离**：模拟任一外部系统不可用，验证只有对应模块降级、其他模块正常（对应第 3.2 节）。
- **容量**：第 8 节数字必须来自 k6 实测报告，不接受估算。
- **边界同步**：本文件第 2、5 节变化时，PR 必须同时包含本文件改动，否则阻断合并。
